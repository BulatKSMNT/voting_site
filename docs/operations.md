# Результаты, история голосований и журналы

Проведение мероприятия с 25 выступлениями, отбором 8 и 2 участников и финалом
описано отдельно в [инструкции организатора](event-guide.md).

## Где смотреть голосование

Откройте `/admin/` → «Rounds» → «Открыть карточку голосования» у нужного раунда.
На карточке видны результаты и таблица «Кто за кого проголосовал»: Telegram ID,
участник, выбор и время UTC. Снимки и техническая история находятся в сворачиваемых
разделах. Отказы и служебные события не смешиваются с принятыми голосами.

Ссылка «Версия …» показывает сохранённый итог на момент завершения, а не повторный
подсчёт сегодняшних данных. После восстановления раунда следующее завершение
создаёт новую версию. Результаты и голоса выгружаются из одной выбранной версии.
Новые снимки содержат исходные голоса с Telegram ID, имена, состав и параметры
раунда. Они сохраняются даже после удаления исходных записей. Старые снимки без
списка голосов явно помечены: детализация задним числом не восстанавливается.
Выгрузка технической истории содержит все события раунда независимо от снимка.

### Скачать понятный отчёт и проверить результаты по файлу

В боте: **`/export` → выбрать мероприятие** в личном чате. Только для главных администраторов.
Архивные мероприятия тоже доступны. В админке: **Campaigns → «Скачать результаты
и голоса»**; в карточке раунда можно скачать весь тур/раунд или всё мероприятие.

ZIP содержит:

- **Результаты.csv** — итоги по турам, места, «За», «Против», проход по баллам и
  выбор администратора. Индивидуальные выступления не дублируют общую таблицу тура.
- **Голоса.csv** — одна строка на принятую запись голоса: Telegram ID, участник,
  «Да»/«Нет» или «За участника», время и ID. Для старых переносов указан исходный
  голос ID: такой перенос не является новым выбором зрителя.
- **Данные.json** — составы, настройки подсчёта, голоса и версии снимков.
- **Как читать отчёт.txt** — пояснения к файлам.

CSV открывается в Excel (UTF-8 с BOM, разделитель `;`). Экспорт активного тура
фиксирует согласованное состояние PostgreSQL на момент выгрузки и не останавливает
приём голосов. До завершения тура места и проходящие участники предварительные.

Распакуйте архив и выполните из каталога проекта:

```bash
python manage.py recount_report /путь/Данные.json > пересчитанные-результаты.csv
```

Команда не обращается к БД и ничего в ней не меняет: пересчитывает «За»/«Против»
из файла, сохраняет нулевые результаты и проверяет совпадение с выгруженными
итогами. У каждого тура собственный набор `votes`; голоса разных версий снимков
складывать нельзя. `result_participant_id` связывает голос с участником итоговой
таблицы (в индивидуальном туре он отличается от ID выступающего в своём раунде).
Выбор администратора и правило топ-N сохраняются отдельно от голосов.

Архив позволяет восстановить таблицу результатов. Автоматического импорта в рабочую
БД нет; полное восстановление сервера делается из резервной копии PostgreSQL.

Для доступа нужны права просмотра Round, Vote, AuditEvent, RoundResultSnapshot.
Суперпользователь уже имеет их. Журнал и снимки доступны в админке только для чтения.
После удаления раунда они остаются в разделах «Журнал голосований» и «Снимки
результатов»; ищите по `round_id`/`campaign_id`. Эти разделы позволяют смотреть и
удалённые голосования, для которых карточка исходного объекта уже недоступна.

Аудит начинается после обновления. Старые голоса и кампании сохраняются, но
исторические снимки и происхождение старых переносов не выдумываются задним числом.
Первое последующее завершение создаст снимок имеющегося состояния.

## Общедоступные и приватные кампании

Режим задаётся у кампании и действует во всех её раундах:

- **Общедоступный** (по умолчанию) — голосовать могут все пользователи бота.
- **Приватный** — голосовать могут только Telegram ID из списка кампании.
  Пустой список закрывает приём голосов для всех, включая администраторов.

В Django Admin откройте **Campaigns → нужная кампания**. Выберите «Доступ к
голосованию», заполните «Допущенные Telegram ID» и сохраните. Можно вставить
ID по одному на строку или через пробел, запятую, точку с запятой. Повторы
удаляются автоматически. Username не подходит; пользователь узнаёт ID через `/myid`.
Для редактирования нужны права изменения Campaign или аккаунт суперпользователя.

В личном чате с ботом главный администратор (`FULL_ADMIN_IDS`) вызывает
`/campaign_access`, выбирает кампанию, затем режим и «Добавить ID» / «Удалить ID».
Можно добавлять несколько порций ID; они объединяются с существующим списком.
Кнопка «Скачать список ID» присылает TXT. Модераторы из `LIMITED_ADMIN_IDS` не могут
менять доступ или получать список. Для нового мероприятия создавайте отдельную
кампанию — её список независим от предыдущей.

Режим и список можно менять во время мероприятия. Исключение пользователя запрещает
его следующие голоса, но не удаляет уже принятые. Возврат к общедоступному режиму
сохраняет список для последующего включения приватного. Администратор, желающий
голосовать в приватной кампании, тоже должен добавить собственный ID.

Допуск проверяется в API непосредственно перед записью голоса, поэтому старые
кнопки Telegram не обходят запрет. Одновременная смена доступа и запись голоса
упорядочиваются транзакцией: голос, записанный до отзыва доступа, остаётся учтённым.
Отказ сохраняется как `vote.rejected` с `reason_code=voter_not_allowed`, а изменение
настроек — как `campaign.updated` с прежними и новыми значениями. Список ID доступен
в закрытой админке/API управления, публичные ответы его не содержат.

Приватный режим ограничивает приём голосов. Показ опубликованных результатов на
сайте и в боте, завершение раундов, определение победителей и переносы сохраняют
прежнее поведение. Перенос исторического голоса не требует повторного допуска.

Для интеграций главного администратора: `PATCH /voting/api/campaigns/<id>/access/`
принимает `{"access_mode":"private"}` или
`{"operation":"add","telegram_ids":[123456789,987654321]}` (также `remove`).
Обычный `PATCH /voting/api/campaigns/<id>/` с `allowed_telegram_ids` заменяет весь
список. Неверный ID отклоняет весь запрос без частичного изменения списка.

## Куда попадают многочисленные запросы без голосования

| Данные | Где хранятся |
|---|---|
| Принятые голоса, изменения, переносы, удаления, отказы в конкретном раунде | Таблица AuditEvent в PostgreSQL |
| Итоги каждого завершения | Таблица RoundResultSnapshot |
| Обычные сообщения боту, обновление страницы, запрос меню, «нет активного раунда», ограничение частоты чтения | `logs/traffic/web-<PID>.jsonl*`, `logs/traffic/bot-<PID>.jsonl*` |
| Действия, ошибки API/Telegram, отказ в правах, traceback | `logs/web-<PID>.jsonl*`, `logs/bot-<PID>.jsonl*` и stdout/stderr контейнеров |

Ожидаемый `404` с кодом `no_active_round` — обычная активность. Он не создаёт строку
аудита в БД и не попадает в основной лог. Поэтому бот может оставаться включённым
между мероприятиями. Ошибки авторизации, сетевые ошибки и `500` остаются видимыми
в основном журнале даже в этот период.

Каждая строка — JSON; `request_id` связывает Telegram-обработчик и HTTP-запросы API.
Время записывается в UTC с поясом, Django Admin показывает время в Europe/Moscow.
В журнале нет исходных текстов сообщений, username и заголовка Authorization.
Telegram ID нужен для разбора действий и доступен только в закрытых журналах/админке.

Для Docker:

```bash
docker compose logs --tail=100 -f web bot
docker compose exec web sh -c 'tail -n 50 /app/logs/traffic/web-*.jsonl'
docker compose exec bot sh -c 'tail -n 50 /app/logs/traffic/bot-*.jsonl'
```

Для поиска в локальных файлах (если установлен `jq`):

```bash
jq -c 'select(.round_id == 12)' logs/web-*.jsonl*
jq -c 'select(.request_id == "нужный-request-id")' logs/*.jsonl* logs/traffic/*.jsonl*
```

Файлы отдельных процессов исключают совместную ротацию одного файла двумя
Gunicorn worker. Запускайте Gunicorn без `--preload`, как в Compose. При нескольких
репликах web каждой реплике нужен отдельный каталог логов или внешний сборщик.

По умолчанию основной журнал: 10 MiB + 5 архивов на процесс; фоновые обращения:
5 MiB + 2 архива на процесс. Ограничение Docker stdout: 10 MiB × 3 файла на контейнер.
Файлы старых завершённых процессов очищаются при запуске соответствующего сервиса:
фоновые старше 7 суток, основные старше 30 суток. Живые процессы не затрагиваются,
их текущие журналы ограничены ротацией по объёму. Это не гарантия хранения всех
обращений за 7 суток: при большом потоке старые строки вытесняются раньше.

Настройки: `TRAFFIC_LOG_MAX_BYTES`, `TRAFFIC_LOG_BACKUPS`, `TRAFFIC_LOG_DAYS`,
`APP_LOG_DAYS`; при необходимости задайте `LOG_DIR`.

Для дополнительной очистки без перезапуска запускайте команду **в контейнере того
сервиса, чьи файлы удаляются**: PID в разных контейнерах принадлежат разным пространствам.

```bash
docker compose exec web python manage.py cleanup_logs --service web --dry-run
docker compose exec bot python manage.py cleanup_logs --service bot --dry-run
# После проверки списка — те же команды без --dry-run.
```

В БД AuditEvent и снимки автоматически не удаляются: они являются историей
голосований, а не краткосрочным техническим логом. Резервируйте их вместе с PostgreSQL.

## Обновление существующего развёртывания

Бот и API обновляются совместно. Новый API проверяет Telegram-роль на сервере, а бот
передаёт `X-Telegram-User-ID` с общим сервисным токеном. `FULL_ADMIN_IDS`,
`LIMITED_ADMIN_IDS` и `DJANGO_API_TOKEN` должны совпадать в окружениях web и bot.
Заголовок пользователя принимается только для токена, совпадающего с
`DJANGO_API_TOKEN`. Произвольный токен обычного Django-пользователя не даёт прав
управления; прямой административный API-доступ предусмотрен для staff-пользователя.

Миграция `0006` добавляет журнал, операции, снимки и поля происхождения.
Миграция `0007` добавляет режим доступа и список Telegram ID кампании. Существующие
кампании остаются общедоступными. Миграции не удаляют голоса, раунды и результаты.
Миграция `0008` добавляет лимит выбора (по умолчанию 3), параметры туров мероприятия,
связи переходов и выбор главного администратора. Старые раунды сохраняются обычными;
новый сценарий готовится в отдельной пустой кампании.

```bash
# Из каталога проекта на сервере. Сначала получить резервную копию БД.
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > backup-before-audit.sql
# Остановить входящие действия на время совместного обновления.
docker compose stop bot web
docker compose build web bot
docker compose up -d db cache
docker compose run --rm web python manage.py migrate
docker compose up -d web bot
```

Compose добавляет небольшой Redis для общих счётчиков ограничения частоты между
Gunicorn worker. Порты Redis и PostgreSQL наружу не публикуются. Голоса и аудит
хранятся в PostgreSQL, не в Redis. При локальном запуске без `CACHE_URL` используется
память одного процесса; для нескольких процессов задайте общий Redis URL.

Квоты разделены по пользователям и видам запросов: чтение 120/мин, голосование
60/мин, управление 120/мин, анонимные запросы 60/мин. Управляются переменными
`API_READ_RATE`, `API_VOTE_RATE`, `API_MANAGE_RATE`, `API_ANON_RATE`. Фоновое чтение
одного пользователя не расходует квоту голосования других пользователей.

Повтор одного и того же завершения/переноса в пределах одного открытия раунда
возвращает ранее сохранённый результат. Если опубликованный стандартный раунд
получил новые голоса/участников, его повторное завершение пересчитывает итог и
сохраняет новую версию, как и раньше. Новое открытие создаёт новый цикл; перенос
после него возможен снова. Не предусмотрены автоматические повторы произвольных
POST-запросов после таймаута. При ошибке подтверждения Telegram уже записанный голос
не отправляется повторно.

## Проверки

SQLite (тесты реальных блокировок будут пропущены):

```bash
SECRET_KEY=test-only DEBUG=False DB_ENGINE=sqlite python manage.py test voting tg_bot --settings=core.test_settings
```

PostgreSQL: задайте переменные `POSTGRES_*` для отдельной тестовой БД и пользователя
с правом создания тестовой БД, затем:

```bash
SECRET_KEY=test-only DEBUG=False DB_ENGINE=postgres python manage.py test voting tg_bot --settings=core.test_postgres_settings
python manage.py makemigrations --check --dry-run
```

Тесты Telegram используют подменённые вызовы API; реальные сообщения не отправляют.
Проверяются запрет повторного голоса, несколько выбранных участников, «да/нет»,
ничьи, переносы с голосами и без, восстановление, неизменность старого снимка,
удаление с сохранением аудита, роли callback/FSM/API, разделение и ротация логов,
независимость квот, приватный доступ, права управления списком и сохранность голосов
при отзыве допуска. На PostgreSQL также проверяются конкурентные
голосование/закрытие/перенос и отзыв доступа одновременно с голосованием.

Алгоритм победителей сохранён. `/export` выгружает архив выбранного мероприятия;
старый API `rounds/export_csv` оставлен для совместимости интеграций. Подробные
выгрузки добавлены отдельно в карточку раунда.
